# Detalhamento arquitetural — decisões e invariantes por módulo

Consultado sob demanda. Este texto era o corpo do `CLAUDE.md` até 2026-10-15 e foi movido para cá **sem alteração**,
para que as instruções carregadas em toda sessão fiquem curtas. Ele preserva as decisões e invariantes de cada
módulo, rota, nó e prova automatizada. O dicionário do banco e a tabela de módulos ficam em
`docs/referencia-tecnica.md` (conferida por `teste-consistencia-docs.js`). Ao mudar um módulo, atualize o trecho
correspondente aqui (e, se for regra essencial, o resumo no `CLAUDE.md`).

## Architecture

**Single giant `index.html`** (~100KB) contains markup for every route as `.page-section` elements, plus an inline SVG library (icons and the game's character art/gradients). It loads:
1. `forca-agil/head-init.js` early in `<head>`.
2. The Firebase **compat** SDKs (app/database/auth) from gstatic, then `firebase.js`.
3. All feature scripts in `forca-agil/` as plain global `<script>` tags, in a specific order that matters because there is no bundler resolving dependencies — each file attaches functions to `window.fa*` namespaces (e.g. `window.faAuth`, `window.faStore`) that later scripts rely on: `firebase.js` → `turmas-util.js` → `roteiro.js` → `router.js` → `auth.js` → `stars.js` → `app.js` → `home-nav.js`/`conteudos-nav.js` → `repo.js` → `game-data.js`/`game.js` → `qrcode.min.js` → `certif.js` → `admin.js` → `avaliacao.js` → `checkin.js` → `pedidos.js` → `dashboard.js` → `motor-posicionamento-nucleo.js` (must precede `questionarios-config.js` and `avaliacao-posicionamento.js`) → `objetos-organizacionais-nucleo.js` (Porta 2, pure; needs the motor nucleus) → `governanca-posicionamento.js` → `questionarios-config.js` → `naturezas-config.js` → `motor-arquitetura.js` → `classificacoes.js` (must precede `avaliacao-produto.js`, `taxonomia.js` and `avaliacao-squad.js`) → `avaliacao-produto.js` → `taxonomia-definicao.js` (puro: monta a publicação da definição única e o histórico; precede `taxonomia.js`) → `taxonomia.js` → `motor-posicionamento.js` → `posicionamentos.js` → `motor-squad.js` → `avaliacao-squad.js` → `exportacoes-posicionamento.js` → `posicionamento-servicos.js` (B1: the Posicionamento screen's only door to Firebase — `gravar`/`novaChave`/`lerUmaVez`/`ouvir`; no business rules) → `analises-organizacionais-nucleo.js` → `analises-organizacionais-firebase.js` → `analises-organizacionais.js` (Porta 2 · Análise Organizacional at `#avaliacoes?an=`, behind the homologation marker `analises-organizacionais-config/habilitacao` — absent = DESLIGADO, enforced by the rules; see `docs/analises-organizacionais-contratos.md`) → `avaliacao-posicionamento.js` → `estruturas-nucleo.js` → `estruturas-casos-de-uso.js` → `estruturas-firebase.js` → `mapa-floresta-demo.js` (fictitious in-memory example data for the 1st visual Mapa) → `mapa-floresta.js` (Catálogo preparatório do Mapa da Floresta — read-only, `#avaliacoes?mf=catalogo`; see below) → `estruturas-tela.js` → `aluno.js` → `facilitador.js` → `aposta.js` → `init.js` (bootstraps on `DOMContentLoaded`).

**Routing** (`forca-agil/router.js`): hash-based router over a fixed page list (`home`, `turmas`, `conteudos`, `treinamento`, `repositorio`, `avaliacao`, `avaliacoes`, `minha-area`, `ajuda`, `admin`, `facilitador`, `checkin`). `navigate()`/`show()` toggle `.page-section[hidden]` and enforce access control on both programmatic navigation and direct hash access (so refreshing on a gated route doesn't leak content while Firebase Auth is still resolving). Late access info (login ready, admin list, Avaliação profile, enrollment, facilitador) re-runs the decision with `show(route, true)`: if the person stays on the same page it does **not** scroll to the top (on slow networks that arrived seconds later and threw people back up mid-scroll); a real page change still starts at the top (`teste-rolagem-decisao-tardia.js`). Likewise, a Back/Forward between two Arquitetura areas (`#admin?arq=…` → `#admin?arq=…`) does not scroll to the top: the screen positions itself on `popstate`, and the `hashchange` that arrives later (slow machine) used to undo it (`teste-rolagem-voltar-carregamento.js`).

**Auth & access control** (`forca-agil/auth.js`): wraps Firebase Auth (compat SDK) behind `window.faAuth`. Access has four independent dimensions, not a ladder (see `docs/referencia-tecnica.md`): authentication (session or not); participation — `member` (default) or `enrolled` (confirmed participant in a turma, read from the `turmas`/`turmas-interesse` RTDB nodes; admins count as `enrolled`); functional profiles (below); and admin privilege (`admin`). Admins are a hardcoded email allowlist plus entries in the `fa-admins` RTDB node. `conteudos`, `treinamento` and `avaliacao` routes require `enrolled` or higher. `isFacilitador()` (`fa-facilitadores` node) is a separate, low-cost flag orthogonal to the three levels — it only grants access to the `#facilitador` route (like `isDiretor()`/`isAdmin()` for their own routes), it does **not** mean the person is on any turma's team. Avaliação de Produto/Serviço has its own, independent access list — node `fa-avaliacao-autorizados/<emailKey>` with `tipo` `'avaliacao'` or `'avaliacao-arquitetura'` (read through `faAuth.getAvaliacaoTipo()`/`podeAvaliacao()`/`podeArquitetura()`/`isAdminRestrito()`, with `isAvaliacaoReady()` for the "don't know yet ≠ no access" rule; the own record is listened to live with `.on('value')`, so granting, changing or removing access updates menu and route without reload) — used by the `#avaliacoes` route (menu item "Avaliação"; `#avaliacao` is the workshop-feedback form, labelled "Avaliar oficina"). `#avaliacoes` itself is the **Início da Avaliação**, organized by the person's work, not by features (no DB read): "Continuar ou consultar" → the Jornada; "Começar um trabalho novo" → natureza P1–P16 (`?nova=1`) or atuação organizacional O1–O9 (`?po=atuacoes`, button only for who writes Posicionamento); the two entry paths are named (Caminho 1 Produto/Serviço, Caminho 2 atuação; "Porta 2" secondary) with "Como o sistema funciona" (one block: each activity next to what sustains it in ADMIN, in plain words; ADMIN area names are links only for profiles that can enter; entering ADMIN from those links shows "← Voltar ao Início de Avaliações" via a history-state marker — not steps); "Consultar registros completos" — a navigable picture of how the subjects relate (Produto/Serviço → Posicionamento → Mapa as possibilities, never mandatory steps; Adequação à Squad as a side branch of the Linha result only, off the path to the Mapa) → the P1–P16 list, now at `#avaliacoes?av=lista` (search, filters, Exportar, Lixeira), Posicionamentos (`?po=lista`), Adequação à Squad (`?sq=lista`) and the Mapa; every other address is unchanged, and the Jornada offers "Acessar Adequação à Squad" only for Linha-branch effective positioning (`teste-avaliacao-inicio.js`). Admin geral has full access without being on the list. `avaliacao` *evaluates* (list, new, continue, reavaliar, exclude/restore, reprocess, export, and the Adequação à Squad evaluation) but sees curadoria (natureza complementar, especialização/papel estrutural) and the final architectural decision read-only; `avaliacao-arquitetura` also curates and decides and, in `#admin`, sees **only** the Arquitetura tab. The old `consulta`/`avaliador`/`gestor` ladder (`fa-avaliacao-acessos`) is legacy, no longer read, and grants nothing. This is enforced by `database.rules.json`, not just by hidden buttons (`.github/scripts/teste-rules-perfis-avaliacao.js` and `teste-rules-avaliacoes.js` prove it on the RTDB emulator); "Usuários autorizados" is admin-geral only. `avaliacao-produto.js` and `avaliacao-squad.js` each run as two instances — operational (`#avaliacoes`: the evaluations, Squad included) and admin (ADMIN › Avaliação e Mapa: questionnaires, motors incl. Motor de Squad, naturezas, "Documentação e mapas" — nodes `arquitetura-documentos` (https link only, archive instead of delete) and append-only `arquitetura-documentos-auditoria` — plus "Usuários autorizados"). Each Arquitetura subscreen has a minimal address `#admin?arq=<área>` (`inicio`, `questionarios`, `motores`, `motor-squad`, `naturezas`, `usuarios`, `documentacao`) so F5 keeps the screen and browser Back moves within ADMIN; those history entries are `history.scrollRestoration = 'manual'` (the mode is per entry — what counts is the entry you go back TO), because the screen positions itself and, after an F5 on a slow network, the browser's automatic restoration only ran at the end of loading and scrolled over the screen and over the person (`teste-rolagem-voltar-carregamento.js`). Likewise, Adequação à Squad inside `#avaliacoes` has its own address `#avaliacoes?sq=lista` / `?sq=<chave>` (F5, direct link — slow read shows "Carregando…", never "não encontrada" — and browser Back/Forward; a new unsaved one has none) and, while open, retitles the page header to "Adequação à Squad" (`teste-squad-endereco.js`). The "Documentação e mapas" screen opens with the "Mapa da Floresta" definition card, read from `arquitetura-definicoes/MAPA_FLORESTA` (stable key; título, definição, nota, link are data, edited on the card and audited in append-only `arquitetura-definicoes-auditoria`; while the node does not exist yet the card shows the factory value `PADRAO_MAPA_FLORESTA`, flagged "ainda não salvo no banco" — never while the read is pending or failed; `teste-mapa-floresta.js`). Every history starts collapsed ("Histórico — N alterações", N = 0 included); what was opened is kept only on the same screen and item. Actual participation in a turma's facilitation team (role `responsavel` or `facilitador`, one responsible per turma) lives in the `turmas-equipe` RTDB node, keyed by turma — see `forca-agil/roteiro.js`.

**Data layer**: Firebase Realtime Database is the only backend (project `kyber-agil`, config in `forca-agil/firebase.js`, security rules in `database.rules.json`). Feature scripts read/write the DB directly from the client (e.g. `turmas-util.js`, `admin.js`, `checkin.js`, `dashboard.js`). The only server-side code is the B4 **trusted boundary** in `functions/` (Cloud Functions 2nd gen, `us-central1`, its own `package.json` — the site itself still has no build or package manager): `fronteira.js` (core, independent of Cloud Functions: `validarRedacaoPublicada`, `conferirEntradaEmVigor` — records only its verdict in the audit, never touches vigência/evaluations/proposal — `ativarEntradaEmVigor` — H3-b: ONE atomic multipath write (vigência + `posicionamento-motor-ativacoes/<proposal>` + `ativacao` audit), consuming the proposal once, also used for the governed return to v1; **switched off in code**, `ATIVACAO_HABILITADA = false`, and the screen shows "Ativar" only when the server reports it enabled — and `concluirAvaliacaoPosicionamento`, which concludes motor ≥ 2 evaluations (the screen cannot) with the screen's own nucleus), `index.js` (onCall wiring; caller identity = the auth token; the server READS with the full Admin SDK but WRITES through a second Admin SDK app with `databaseAuthVariableOverride: { uid: 'fronteira-confiavel' }`, so every server write goes through `database.rules.json`, which lets that identity write only the boundary's nodes) and `modulos-site.js` (runs the SAME site files on the server — copied to `functions/site/` by `.github/scripts/copiar-modulos-fronteira.js` in predeploy, never committed). The site calls it only through `faServicosPosicionamento.executar`; only the `fronteira-confiavel` identity writes `posicionamento-motor-redacao-validada`, `posicionamento-motor-ativacoes`, `posicionamento-motor-vigencia` and concludes motor ≥ 2 evaluations (H3-b: the screens read the version in force from `posicionamento-motor-vigencia` — never assume v1 while it is pending or refused; new evaluations are born in it as `versaoMotor`, old ones change only by an explicit "Atualizar com motor atual"; `teste-rules-posicionamento-v2.js` on the emulator) (`teste-fronteira-posicionamento.js` on the database+auth+functions emulators, `teste-fronteira-estrutura.js`).

**Porta 2 of the Posicionamento (PR 1 data + rules, PR 2 recognition, PR 3 journey):** `objetos-organizacionais-nucleo.js` (`window.faObjetosOrganizacionaisNucleo`, pure, loaded by `index.html`) — an organizational ACTUATION/responsibility positioned by O1–O9 WITHOUT P1–P16: node `objetos-organizacionais` (identity, `revisao`, server time, append-only `objetos-organizacionais-auditoria`, close with reason = final, never deleted; closing refused with an open Posicionamento draft or an active responsible structure; a closed object takes no new Posicionamento, Squad evaluation or vínculo) and `objetos-organizacionais-por-referencia` (optional, informative, fixed link to a P1–P16 item: one active object per item, refused if the item has a vigente or draft Posicionamento; while it exists Porta 1 cannot start that item). In `avaliacoes-posicionamento`, `origem: 'objeto-organizacional'` swaps the P1–P16 gate for "active object" and `hipoteseInicial` (8 firm codes or `NAO_SEI`) is required there, optional in Porta 1, fixed, never an input to the motor (the rules still check the result is exactly the motor's). Rules built by `.github/scripts/montar-regras-objetos-organizacionais.js` (+ `montar-regras-posicionamento.js`); proofs `teste-rules-objetos-organizacionais.js` (emulator) and `teste-objetos-organizacionais-nucleo.js`. PR 2 (recognition): the Posicionamento list/ficha/draft show the "Atuação organizacional" block (no P1–P16 gate; conclusion gated by "active object"; no Reavaliar until PR 3 brings the new hypothesis), the Catálogo lists the objects (and marks the P1–P16 item an object references), the Mapa/structure ficha list them under "Produtos, serviços e atuações", exports carry Origem/atuação/"Não se aplica", the Squad shortcut works without P1–P16, and the trusted boundary refuses Porta 2 with `PORTA2_NAO_SUPORTADA` (`teste-porta2-reconhecimento.js`, section 8f of `teste-estruturas-jornada.js`). PR 3 (journey): the list offers both doors; `#avaliacoes?po=atuacoes[&item=<id>]`, `?po=nova-atuacao`, `?po=editar-atuacao&item=<id>` create/edit/close the actuation (reference picker disables items with a Posicionamento or draft, with the reason); the initial hypothesis is mandatory in BOTH doors for every new record (rules too; only the dormant "Atualizar com motor atual" carries the previous one), never shown during the questions, compared in the result (`#poBlocoHipotese`: confirmada / não confirmada with the motor rule / A validar / sem hipótese / não registrada); Porta 2 re-evaluation asks a new hypothesis; result Estratégia de Clientes shows the provisional note `#poNotaEstrategiaClientes` (`teste-porta2-jornada.js`).

**Feature scripts** roughly map one file per route/feature: `game.js`/`game-data.js` (quiz, XP, ranks), `admin.js` (admin dashboard — turmas, participants, status/destino filters, equipe de facilitação, roteiro), `avaliacao.js` (workshop feedback), `avaliacao-produto.js`/`avaliacao-squad.js` (Avaliação de Produto/Serviço and Adequação à Squad — two instances each, see Auth above), `classificacoes.js` (`window.faClassificacoes` — **single source of the NAME and DEFINITION of the Avaliação's classifications: the Taxonomia Arquitetural concept with the SAME code as the motor's camada** (no link table); `CAMADAS` in `avaliacao-produto.js` is only the motor's catalog of codes + a factory label used as contingency; also the "Conceito-base" card atop the `#avaliacoes` list (name + vigente definition of `produto-principal`, no definition text in code — no answer shows "Carregando…"/"indisponível", never a factory definition); reads live, per code, only `taxonomia/arquitetural/conceitos/<id>/{nome,ativo,definicao/texto}` — the single official definition in force (no source catalog since the Taxonomia simplification); slow/denied/missing → factory label + discreet "Rótulo de contingência" notice, never touching result, code, decision or history; the motor never reads the Taxonomia; a conclusion saves `camadaSugerida.id` + the name resolved then (`label`, never rewritten), and screens/PDF/Excel show the current name plus "na conclusão: X" / column "Rótulo registrado na conclusão" when they differ; `database.rules.json` grants that granular read — no list of codes — to admin geral, `avaliacao` and `avaliacao-arquitetura`, proved in `teste-rules-perfis-avaliacao.js`; the old motor "Editar textos" label was a dead copy and its UI is gone; `teste-classificacoes-fonte-unica.js`), `checkin.js` (QR check-in, uses `qrcode.min.js`), `certif.js` (certificate generation from `cert-template-v3.png`), `manual.js` (ADMIN › Manual — documentation for people, by area, built on the four access dimensions; points to official sources and automated proofs, never a source of rules; **not** in `index.html`: `admin.js` injects it the first time the tab opens), `pedidos.js`, `dashboard.js`, `aluno.js` (aluno's "Minha Área"), `taxonomia.js` (Admin → Taxonomia, só admin: dicionário dos conceitos em dois domínios separados — arquitetural "o que é o item?" e organizacional "que tipo de estrutura é esta?" — com o nó `taxonomia` do banco; **cada conceito tem UMA definição oficial vigente, versionada, com histórico imutável** (modelo simplificado, nos dois domínios): `conceitos/<c>/definicao = {texto, versao, publicadaEm, publicadaPor}` e `definicoes/<c>/v<n>` (mesmo texto/versão/publicação + `origem` `publicacao`|`carga-inicial`|`migracao`, `motivo` opcional, `legado` só da migração) — sem catálogo de fontes, situação, rótulo, tipo de redação, promoção manual nem arquivamento; as regras exigem versão = anterior + 1 (compare-and-set) com a entrada `v<n>` nova na MESMA gravação, `publicadaPor` = quem grava, entrada de histórico nunca reescrita e definição nunca apagada; a tela tem um fluxo único — "Atualizar definição" (ou "Registrar definição") → conferir anterior × proposta → "Publicar nova definição" (auditoria `definicao_publicada` na mesma gravação; recusa se outra pessoa publicou antes; clique repetido bloqueado), "Última atualização: data · responsável · versão" e "Histórico de alterações — N alterações" recolhido (com "Antes da simplificação da Taxonomia" para as trocas de vigência antigas, textos lidos do arquivo de migração); a tela tem **três espaços** com volta clara ("← Voltar ao catálogo"), sem formulário, ação ou fonte de dados duplicados e sem persistência nova: **Catálogo** (cabeçalho compacto "Taxonomia", seletor Organizacional/Arquitetural, busca por nome ou código; no computador lista à esquerda e ficha à direita, a 375 px a ficha abre em vista própria com "← Voltar aos conceitos") cuja ficha mostra SÓ nome e localização na hierarquia, "O que é?" (a definição oficial, uma vez; sem ela, "Não há definição oficial disponível para este conceito." — nada inventado), hierarquia (pai e filhos clicáveis, não confundir com relações), "Comparar com outro conceito" (dois conceitos do mesmo domínio: nome, definição completa e hierarquia de cada um; sem diferença inventada nem classificação automática; sem definição de um dos lados ou com textos idênticos: "As definições disponíveis não são suficientes para estabelecer uma distinção clara. Essa diferenciação depende de revisão arquitetural."; nunca grava) e "Administrar conceito" (secundário, só para quem pode) — nunca código, integração, atributos, Papel/Origem, histórico, relações, pergunta/critérios/observações nem ações de edição; **Administração** ("Administrar — <nome oficial>", abas Conteúdo / Perfil e Relações (só organizacional) / Histórico e governança): Conteúdo = identificação (código, camada, situação, proteções), definição (fluxo versionado "Atualizar definição") e "Pergunta, critérios e observações" (nome, pergunta, critérios, nota, observações por "Editar informações", separado da definição); Perfil = os 13 atributos numa tabela agrupada (Estado, Valor, Papel, Origem; os sem registro aparecem aqui) com UMA ação "Gerenciar perfil" (todos os atributos num formulário, salvo de uma vez: só os alterados, um evento de auditoria por atributo, nenhum registro vazio, releitura no servidor antes de gravar contra concorrência; `teste-taxonomia-atributos.js`); Relações = "Relações registradas entre conceitos" em frase "A — tipo — B", sem códigos, com o aviso de que são vínculos cadastrados (não comprovam relações entre áreas reais nem são regras universais) e ações diretas (nova, "Substituir" = encerrar a atual e criar a nova, com o efeito explicado antes, encerrar; releitura no servidor antes de gravar); Histórico e governança = histórico único recolhido (anterior → novo, campo em português, motivo; a v1 migrada é "Registro inicial", não alteração; criação de fonte e troca de vigência do modelo antigo em "Detalhes técnicos anteriores à simplificação"; nada é reescrito no banco) e "Situação do conceito" (inativar, reativar, alterar camada, protegidos); durante a releitura do domínio depois de uma gravação, a administração espera no lugar ("Carregando o conceito…"); **Integridade e configurações** (só admin, pelo atalho do topo, que diz "requer atenção" quando falta vínculo ou "não foi possível conferir", e nunca "ok" antes de ler os dois lados): "Integração com a Avaliação" (11) e "Integração com o Posicionamento" (10) — resumo discreto quando completo, aviso destacado com o impacto quando não, só as ações autorizadas que já existiam, nunca recriando vínculos sozinha — e "Dados e manutenção" (exportar Excel/JSON, histórico global, carga inicial) (`teste-taxonomia-ficha.js`, semente fictícia `semente-taxonomia-ficha.js`, navegação comum dos testes em `taxonomia-tela.js`) — mais a administração discreta (inativar, camada) no fim (`teste-taxonomia-ficha.js`, semente fictícia `semente-taxonomia-ficha.js`); montagem pura em `taxonomia-definicao.js` (`teste-taxonomia-definicao.js`, regras: `teste-rules-taxonomia-definicoes.js`); **migração controlada** do modelo de fontes (`.github/scripts/migracao-taxonomia-definicoes.js`, workflow manual `taxonomia-migracao-definicoes.yml`: exportar → simular (padrão) → executar → verificar → reverter; a vigente apontada vira v1 (`origem: migracao`), fontes nunca vigentes NÃO viram versões, duas vigentes/ponteiro órfão param tudo; todo o legado vai intacto para `taxonomia-arquivo-migracao` (só leitura do admin), com backup em artefato; reverter só enquanto nenhuma versão nova foi publicada) — só roda em produção com autorização da dona; carga inicial por importação única, sem conteúdo conceitual no código; "Exportar Taxonomia" ("Baixar Excel" / "Baixar JSON", os dois domínios qualquer que seja a aba; formato versão 2), só leitura — o Excel abre na aba "Visão consolidada por conceito" (uma linha por conceito; cabeçalho congelado, colunas fixas, autofiltro e quebra de linha gravados no XML via `XLSX.CFB`, porque a SheetJS CE não grava painel nem estilo; se o ajuste falhar, baixa o arquivo completo sem ele e avisa "Atenção"), aba "Definições" com uma linha por versão (a vigente marcada), e o JSON traz o nó `taxonomia` intacto mais `conceitosConsolidados` (`definicaoVigente`, `historicoDefinicao`, `integridadeDefinicao`); ficha na ordem cabeçalho → definição oficial → como reconhecer → perfil → relações → histórico recolhido; **governança (Etapa 5), garantida pelas regras do banco:** `avaliacao-classificacoes/<código>` é a ligação canônica classificação do motor ↔ conceito arquitetural de MESMO código — só governança (`registradoEm/Por`, `auditoriaId`, nunca nome/definição), só admin geral, registrada uma vez pelo botão em "Integração com a Avaliação" (prévia, idempotente; tudo certo → só "11 de 11 classificações conectadas"; faltando → aviso destacado com o impacto, nunca resumo positivo, e "Proteção da Avaliação incompleta: X de 11"; nomes em "Ver classificações conectadas", códigos e datas nos detalhes administrativos), nunca alterada nem apagada (encerrar ligação é backlog), histórico append-only em `avaliacao-classificacoes-auditoria`; conceito arquitetural ligado não pode ser inativado; inativar exige motivo (`conceito.inativacao`) e reativar fica registrado (`conceito.reativacao`), ambos apontando (`auditoriaId`) para a auditoria nova da mesma gravação; ## Deploy

Firebase Hosting, project `kyber-agil` (`.firebaserc`). `firebase.json` serves the whole repo root (`"public": "."`) except `scraps/`, `screenshots/`, `uploads/`, `preview-chars.html`, `*.md`, `*.txt`, and dotfiles; it rewrites every path to `/index.html` (the hash router handles the rest) and sets CSP + no-cache headers for `index.html`/JS/CSS.

Deploys are driven entirely by GitHub Actions (`.github/workflows/`), using `firebase-tools@13` and the `FIREBASE_SERVICE_ACCOUNT_KYBER_AGIL` secret — there is no manual deploy step:
- push to `main` → `firebase-deploy.yml` deploys `hosting,database` to the live `kyber-agil` project.
- push to `v2` → `firebase-preview.yml` deploys to preview channel `v2-preview` (30-day expiry).
- push to `v3-quiz` → `firebase-preview-v3.yml` deploys to preview channel `v3quiz` and commits the resulting preview URL into `PREVIEW_URL_V3.txt`.
- Cloud Functions (B4) are **never** deployed by `main`: only by the manual `deploy-functions.yml` (type `IMPLANTAR`, `main` only, `--only functions`), and only after the owner authorizes the infrastructure (Blaze, APIs, roles — read-only diagnosis in `verificar-infra-functions.yml`). `firebase.json` hosting ignores `functions/**`.

`database.rules.json` (RTDB security rules, the readable source) deploys alongside hosting on `main` **as its compacted artifact `database.rules.min.json`** (B2: `firebase.json` points to it; regenerate with `node .github/scripts/regras-compactas.js --gravar database.rules.min.json` after any edit to the source — `teste-regras-compactas.js` fails in CI if they diverge). Published redação of a new Posicionamento motor (`questionarios-config/<código>/motores/<v>/versoes`) is immutable by the rules (`teste-rules-redacao-motor.js`, structural guard `teste-regras-redacao-imutavel.js`): never reintroduce a `.write` on any ancestor of `versoes/<n>`; to stop publications use the admin-geral-only `publicacaoSuspensa`, never loosen the rules. B3: the entry into force of a new Posicionamento motor is governed by `posicionamento-motor-propostas` (proposal bound to the published redação + impact; two approvals in fixed slots `a1`/`a2`, distinct UIDs, the proposer never approves, at least one admin geral checked by the rules; `aberta` → `aprovada`/`retirada`, both final), the one-open-proposal index `posicionamento-motor-proposta-aberta` (released in the same write that approves or withdraws) and append-only `posicionamento-motor-governanca-auditoria`; `posicionamento-motor-vigencia` is write-closed to every client and written only by the `fronteira-confiavel` identity, as a sequence compare-and-set with the activation record and audit in the same write (H3-b) — an approved proposal by itself puts nothing in force (`teste-rules-governanca-motor.js`, rules built by the same `faGovernancaPosicionamento.montar*` the ADMIN screen uses).

## What this is

"Força Ágil" is a vanilla JavaScript single-page site (gamified onboarding/training experience, Star Wars-themed) for Previ. There is **no build step, no bundler, no package manager, no test suite** — the repo is deployed to Firebase Hosting exactly as committed.

## Commands

There is no `package.json` and no local dev/build/lint tooling in this repo (tests: see the hermetic suite below). The only commands that exist are the deploy commands run by CI (see Deploy below) via `npx firebase-tools@13`. To preview locally, serve the repo root over HTTP (e.g. `npx firebase-tools@13 serve` or any static file server) — opening `index.html` via `file://` will break Firebase Auth/CSP.

The hermetic test suite (fake Firebase, no secrets, no network — `.github/scripts/suite-hermetica.json`) runs locally with `node .github/scripts/rodar-suite.js` while the repo root is served on `http://127.0.0.1:8811` (`python3 -m http.server 8811`). It runs every test even after a failure, in parallel by default (cores − 1, max 3; `--processos 1` for sequential), and refuses to run if a `teste-*.js` is neither listed in the suite nor in its `foraDaSuite` with a reason. CI runs the same suite in 4 duration-balanced groups (`testes-automaticos.yml`), plus a non-blocking Smoke against the real Firebase (`.github/scripts/smoke-site-real.js`: logs in as the test admin, checks the main routes load with real data, writes nothing; its checks are kept honest offline by `teste-smoke-seletores.js`). Technical reference for developers/migration (DB dictionary, modules and load order, deploy/CI) lives in `docs/referencia-tecnica.md`, verified by `teste-consistencia-docs.js`; human-only post-deploy checks are in `docs/checklist-pos-deploy.md` and not-yet-automated scenarios in `docs/backlog-testes.md`. There are no Mapa/Testes tabs in the ADMIN anymore (removed in Etapa 6.2).
